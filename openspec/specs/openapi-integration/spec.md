# openapi-integration Specification

## Purpose
Define ASP.NET Core integration requirements so `AddPatchly()` configures System.Text.Json type info resolution for correct OpenAPI schema generation and runtime behavior.
## Requirements
### Requirement: AddPatchly Service Registration

The source generator SHALL emit a `PatchlyServiceCollectionExtensions` class with a `public static IServiceCollection AddPatchly(this IServiceCollection services)` extension method that inserts `PatchlyJsonTypeInfoResolver.Default` at position 0 in the `TypeInfoResolverChain` of ASP.NET Core's HTTP JSON options. The extension method SHALL be gated behind `#if NET8_0_OR_GREATER`.

#### Scenario: AddPatchly configures minimal API JSON options

- **GIVEN** an ASP.NET Core minimal API application
- **WHEN** `builder.Services.AddPatchly()` is called during startup
- **THEN** `PatchlyJsonTypeInfoResolver.Default` is inserted at position 0 in `JsonSerializerOptions.TypeInfoResolverChain` for HTTP JSON options
- **AND** `[PatchDocument]` types deserialize correctly with property tracking

#### Scenario: AddPatchly is not available on NET6/7

- **GIVEN** a project targeting .NET 6 or .NET 7
- **WHEN** the source generator runs
- **THEN** the `PatchlyServiceCollectionExtensions` class is NOT compiled
- **AND** no compilation errors occur

#### Scenario: AddPatchly is generated only when PatchDocument types exist

- **GIVEN** an assembly with one or more `[PatchDocument]` classes
- **WHEN** the source generator runs on NET8+
- **THEN** the `PatchlyServiceCollectionExtensions` class is emitted
- **AND** `AddPatchly()` is available as an extension method on `IServiceCollection`

#### Scenario: AddPatchly is not generated for non-web projects

- **GIVEN** a .NET 8+ console application without ASP.NET Core references
- **AND** one or more `[PatchDocument]` classes
- **WHEN** the source generator runs
- **THEN** `PatchlyServiceCollectionExtensions` is NOT emitted
- **AND** no compilation errors occur
- **AND** the resolver is still generated and usable via manual `JsonSerializerOptions` configuration

### Requirement: Resolver Enables Correct OpenAPI Schemas

When `AddPatchly()` is called, the OpenAPI document generated by ASP.NET Core 9+ SHALL contain correct property definitions for `[PatchDocument]` types instead of empty schemas.

#### Scenario: OpenAPI schema shows all tracked properties

- **GIVEN** an ASP.NET Core 9+ app with `builder.Services.AddPatchly()` and `builder.Services.AddOpenApi()`
- **AND** a `[PatchDocument]` class with `string? FirstName`, `string? LastName`, `int? Age`
- **WHEN** the OpenAPI document is generated at `/openapi/v1.json`
- **THEN** the schema for the patch class has properties `firstName`, `lastName`, `age`
- **AND** each property has the correct type and is nullable

#### Scenario: OpenAPI schema is empty without AddPatchly

- **GIVEN** an ASP.NET Core 9+ app WITHOUT `builder.Services.AddPatchly()` but WITH `builder.Services.AddOpenApi()`
- **AND** a `[PatchDocument]` class
- **WHEN** the OpenAPI document is generated
- **THEN** the schema for the patch class is empty (`{ }`) due to `[JsonConverter]` producing `Kind = None`

#### Scenario: Deserialization still works without AddPatchly via converter fallback

- **GIVEN** an ASP.NET Core app WITHOUT `builder.Services.AddPatchly()`
- **AND** a `[PatchDocument]` class
- **WHEN** a PATCH request is sent with JSON payload
- **THEN** deserialization works correctly via the `[JsonConverter]` attribute fallback
- **AND** property tracking (`WasProvided`, `Provided`) works as expected
